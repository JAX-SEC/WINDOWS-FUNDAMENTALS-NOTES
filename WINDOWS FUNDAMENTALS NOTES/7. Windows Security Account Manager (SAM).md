The Security Account Manager (SAM) is a critical Windows operating system database housing user account credentials, including usernames and hashed passwords. It helps secure system data in the event of a breach. Managed by the Local Security Authority (LSA), it validates user logins by cross-referencing passwords within the SAM database. Stored in the *c:\\windows\\system32\\config\\SAM* directory and *HKEY\_LOCAL\_MACHINE\\SAM* registry, the SAM file is tightly secured during system runtime, preventing direct copying or relocation. This protection is achieved with exclusive file system locks enforced by the operating system.

The system locks that restrict online copying of the SAM file remain active until the OS encounters a critical error or shutdown. Despite this protection, threat actors may extract password hashes for offline brute-force attacks by dumping the SAM file's on-disk contents using various methods.

Let’s dive deeper into what LM hash and NTLM hash are.

## Windows hashes

LM and NTLM hashes are cryptographic representations of passwords in Windows systems.

**LM hash:** LM hashes represent the oldest form of password storage in Windows, originating from OS/2 in the 1980s; their limited character set makes them susceptible to password-cracking attacks. If accessible, LM hashes can be obtained from the SAM database on a Windows system or the NTDS database on the Domain Controller. Starting with Windows Vista/Server 2008, LM was disabled by default due to its vulnerabilities, but the LM hash is still stored for backward compatibility reasons. Preventing the storage of LM hash is possible by using passwords longer than 14 characters or incorporating specific Unicode characters.

**NTLM hash:** In contemporary Windows operating systems, this hash represents a more secure method of password storage than LM. It is computed based on the entirety of the user-entered password.

## SAM database attacks

**Pass-the-hash** **attack:** In this attack, threat actors retrieve stored hashes from the SAM database on Windows systems and then utilize these stolen hashes to gain unauthorized access to network resources by injecting them into local sessions. This method can affect servers using NTLM or LM authentication across various operating systems, although Windows, due to its Single-Sign-On (SSO) feature, might face increased vulnerability by allowing access to resources with a one-time login.

**Corrupting the SAM database:** A threat actor with administrative access may manipulate the SAM database, creating new accounts, altering passwords, or disabling existing ones. Poor user account management might lead to surplus or obsolete accounts, expanding the attack surface and facilitating unauthorized access.

**Deleting the SAM database:** Prior to the release of Windows 2000, deleting the SAM file allowed threat actors to bypass local authentication, granting access to any account without a password. Microsoft addressed this vulnerability in Windows XP by shutting down the system if an attempt to delete the SAM file occurred. However, threat actors can still delete the SAM file using software utilities such as an emulated virtual device or a boot disk.

### 🔐 1. **What the SAM File Is**

**SAM = Security Account Manager**  
It’s a database file in Windows that stores **user account credentials** — specifically **hashed passwords**.

- **File path:**
    
    ```
    C:\Windows\System32\config\SAM
    ```
    
- It stores **local account usernames and password hashes**.
    
- Passwords are not stored in plain text — they’re **hashed using NTLM (NT Hash)** and sometimes **LM Hash** (old, deprecated).
    

Windows **locks** the SAM file while the system is running, so you can’t just open or copy it when logged in normally.

---

### ⚙️ 2. **The SYSTEM File**

The **SYSTEM** file (also found in `C:\Windows\System32\config\SYSTEM`) is part of the Windows registry hive that contains **system-wide configuration** info — including the **encryption key** that protects the SAM hashes.

Basically:

- SAM = has the **password hashes**
    
- SYSTEM = has the **key** to decrypt those hashes
    

So, if an attacker gets both files, they can **extract the actual password hashes** using tools like `pwdump` or `impacket-secretsdump`.  
That’s why both are valuable in forensic and pentesting scenarios.

---

### 🧱 3. **The SECURITY File**

The **SECURITY** hive (`C:\Windows\System32\config\SECURITY`) stores:

- Local security policies
    
- Access control information
    
- LSA secrets (used for cached service account passwords, etc.)
    

It’s used by the **Local Security Authority Subsystem (LSASS)** to manage authentication and permissions.

---

### 🧠 4. **How They Work Together**

Here’s the simplified relationship:

|Component|Purpose|Location|
|---|---|---|
|**SAM**|Stores user hashes|`C:\Windows\System32\config\SAM`|
|**SYSTEM**|Contains boot/system keys|`C:\Windows\System32\config\SYSTEM`|
|**SECURITY**|Contains LSA secrets and security policy|`C:\Windows\System32\config\SECURITY`|

When a user logs in:

1. LSASS reads the SAM hive.
    
2. Password hash is decrypted using SYSTEM hive key.
    
3. It compares it against what the user entered.
    
4. If hashes match → user authenticated.
    

---

### 🧩 5. **Security Implications**

If an attacker gets access to all three hives (SAM, SYSTEM, SECURITY), they can:

- **Dump password hashes**
    
- **Extract service credentials**
    
- **Perform pass-the-hash attacks**
    
- **Access cached domain credentials**
    

This is why **admin-level access** is dangerous — it gives access to these sensitive hives.

---

### 🧰 6. **Forensics & Pentesting Note**

These files can be copied from an **offline Windows system** (like from a mounted drive or recovery mode).  
Tools commonly used for analysis:

- **impacket-secretsdump**
    
- **pwdump**
    
- **mimikatz**
    
- **reg save** (for legitimate forensic backup)
    

For example (in PowerShell, for backup):

```powershell
reg save HKLM\SAM C:\backup\SAM
reg save HKLM\SYSTEM C:\backup\SYSTEM
```

---

### 🛡️ 7. **Defense Tips**

If you’re hardening or defending:

- Use **BitLocker** (so offline extraction is useless).

- Limit **local admin rights**.

- Disable or rename built-in **Administrator** accounts.

- Use **Windows Hello / Credential Guard**.

- Regularly clear cached credentials.
